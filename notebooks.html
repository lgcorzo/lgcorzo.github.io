FAILURE & FIX EXP-2026-001 · Oct 11, 2026
Repo: lgcorzo/gitops_internal_lgcorzo

FluxCD CI Pipeline: Kubeconform Validation False Positives on Helm Values & Raw Pod Templates

Commit: 4839b91 (fix: exclude Helm values and raw job templates from kubeconform)

1. What I wanted to verify

Enforce strict schema validation on all Kubernetes manifests in GitOps before merging PRs, eliminating malformed manifests and unparseable CRDs via Kubeconform.

2. Architecture & Setup

GitHub Actions CI pipeline running kubeconform -strict with Flux CRD schemas across all *.yaml files discovered under clusters/ and infrastructure/.

3. What actually happened

The pipeline failed systematically on valid Helm values fragments and parameter-injected sandbox job templates (sandbox-job.yaml) because they were not standalone, schema-complete Kubernetes resource documents.

4. Lessons & Limitations

Static AST/schema tools cannot blindly walk recursive Git trees without discriminating between compiled manifests, parameter files, and template fragments. Naive CI gates create friction and noise.

5. Action & Evolution

Restructured file exclusion rules in the workflow to specifically filter out *values*.yaml and raw templated batch jobs, reserving Kubeconform strictly for hydrated/declarative manifests.

# Pipeline pattern update
find clusters infrastructure -type f \( -name "*.yaml" \)
  ! -name "*values*.yaml" ! -path "*/sandbox-job.yaml" | xargs kubeconform
TRADE-OFF DECISION EXP-2026-002 · Oct 13, 2026
Repo: lgcorzo/rust_CACD_autonomous_factory

Cargo Audit Gates vs. Unmaintained Transitive Crates: Managing Real Dependency Trade-offs

Commit: 087e6247 (fix(ci): format qa_observer, update quinn-proto, and ignore unmaintained advisory)

1. What I wanted to verify

Maintain an automated zero-advisory security standard across the Rust factory codebase via automated cargo audit checks on every branch.

2. Architecture & Setup

Rust 2024 autonomous factory workspace with multiple microservices, Hatchet worker integration, and OpenZiti/Quinn networking stack.

3. What actually happened

Transitive dependency unsafe-libyaml triggered RUSTSEC-2024-0449 (unmaintained warning). Upgrading immediately was impossible without upstream breaking changes in YAML parser consumers.

4. Lessons & Limitations

Total automated security cannot mean blind zero-tolerance halts. Real systems require explicit risk acceptance registers (.cargo/audit.toml) with tracked rationale rather than unvetted hacks or blocking all delivery.

5. Industrial Relevance

Directly translates to enterprise software management: automated scanners flag unmaintained packages, but architectural decisions require distinguishing unexploitable parser edges from critical remote CVEs.

ARCHITECTURAL DECISION EXP-2026-003 · Continuous
Architecture: Hatchet Engine vs. Custom State Machine

Durable Orchestration: Evaluating Hatchet DAGs vs. In-House Actor State Machines

1. What I wanted to verify

Whether a custom state machine in Rust (Tokio + Postgres) offers better operational simplicity than adopting an external durable workflow engine (Hatchet) for multi-step agent tasks.

2. Findings & Failure Modes

Custom state machines failed on node eviction during long-running LLM inferences. Replaying partial DAG state without durable step checkpointing required building a full scheduler from scratch.

3. Lessons Learned

Offloading step-level durability and retry backoff to Hatchet drastically reduces bespoke concurrency code in agent executors, freeing focus for spec verification and sandbox containment.

4. Industrial Application Transfer

In manufacturing environments with multi-step CAD/CAM processing, durable execution patterns prevent orphaned compute jobs when worker pods scale or rebalance under load.

SECURITY BENCHMARK EXP-2026-004 · May 2026
Tools: kube-bench (CIS Benchmark v1.8) & Trivy

Kubernetes Control Plane & Worker Node Hardening: CIS Benchmark Audit and RBAC Least-Privilege

Context: Sanitized audit logs and remediation backlog from gitops_internal_lgcorzo/docs/kube-bench and trivy

1. What I wanted to verify

Evaluate cluster security posture against the official CIS Kubernetes Benchmark and NSA hardening guidance, pinpointing control plane authorization drift, non-root pod compliance, and RBAC privilege inflation.

2. Architecture & Methodology

Automated job execution of kube-bench across control plane / worker profiles alongside cluster-wide trivy k8s scans targeting RBAC roles and container runtime configuration.

3. Findings & Gaps Detected

Identified non-compliant control plane defaults: API server authorization permitting permissive modes, anonymous authentication flags active by default, and third-party operator ClusterRoles (e.g. storage and autoscaling controllers) requesting broad wildcard permissions.

4. Remediation & Lessons

Restricted API server flags to strict Node,RBAC modes, disabled anonymous auth, enabled automatic certificate rotation, clamped file permissions to 600, and applied least-privilege scoping to custom ClusterRoles.

5. Industrial Application Transfer

Default lightweight or developer Kubernetes distributions often ship permissive security configurations for developer convenience. In industrial OT/IT integration, automated CIS auditing gates are mandatory before hosting factory telemetry or execution agents.

GITOPS & CRYPTO DISASTER RECOVERY EXP-2026-005 · Dec 2025 – Present
Framework: Bitnami SealedSecrets & FluxCD

Asymmetric Secret Governance in Public Repositories: Testing SealedSecrets Key Rotation & Disaster Recovery

Context: Sanitized procedure from gitops_internal_lgcorzo/docs/sealed_secrets_recovery.md

1. What I wanted to verify

Validate a zero-plaintext-in-Git architecture using Bitnami SealedSecrets and verify cluster migration and disaster recovery protocols without exposing unsealed keys or locking out automation.

2. Architecture & Key Lifecycle

Public/private asymmetric keypair managed in-cluster by the sealed-secrets controller. CI/CD developers encrypt secrets locally using the public certificate; only the in-cluster private key can decrypt them into native Kubernetes secrets.

3. Disaster Recovery Scenario Tested

Simulated total cluster teardown and rebuild from scratch. The primary operational risk tested: if the master sealing key is lost, every encrypted manifest in Git becomes permanently unrecoverable, halting Flux reconciliation.

4. Lessons & Operational Controls

Established an offline out-of-band master key recovery procedure, verified key injection prior to Flux root sync, and tested secret unsealing verification steps to eliminate bootstrap deadlocks.

5. Industrial Application Transfer

Enables strict GitOps compliance in regulated industrial settings: Git repositories can be audited publicly or semi-publicly without risking database passwords, API tokens, or OT gateway credentials.
