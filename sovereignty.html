Fork Policy & Code Quality Governance

Across 72 total repositories in the lab (64 public, 8 private), 42 are maintained as independent forks of principal open-source projects. Here is the engineering rationale for maintaining these forks and the quality controls that govern them.

Status taxonomy

Every operational tier and governance control across this page carries one of four explicit verification tags:

Verified Confirmed by automated CI suites or published evidence files.
Deployed Running and active in live cluster environments.
Implemented Code written, unit-tested, and tracked in the Rust workspace.
Designed Documented in ADRs, specs, or wiki; full validation pending.

Why does the lab fork open-source projects?

Maintaining critical dependencies under sovereign forks protects against breaking upstream changes, unpatched security vulnerabilities, and vendor lock-in.

Deterministic SDD & Schema Contracts

Autonomous agents require strictly typed, deterministic interfaces. In forks like spec-kit and speckit-superpowers-bridge, we lock CLI flags and JSON schemas so agent workflows cannot break unexpectedly from upstream churn.

Verified

Automated Vulnerability Patching

When Dependabot or CodeQL identify CVEs in dependencies, our hourly scanner (GitHub Project 6 + Jules) opens patches immediately. We do not wait weeks for upstream maintainers to merge security updates.

Verified

Uniform Engineering Quality Gates

Every maintained fork enforces the same CI checks: strict linter configs (ruff, clippy), security audits (pip-audit, cargo audit), and SHA-256 hash-pinned lockfiles.

Verified

Insulation from License & Registry Shifts

When upstream vendors change licensing models or deprecate registry tags, our decoupled Go and Python forks compile hermetically to ghcr.io/lgcorzo/* without interruption.

Deployed

What quality rules govern forked repositories?

Each of our 42 forked repositories operates under five non-negotiable engineering rules:

Rule Standard & Requirement Enforcement Mechanism Status
1. Remote & Branch Hygiene Main branches track upstream clean tags. Custom changes are isolated to dedicated feature branches or cleanly rebasing tracking branches. Automated branch protection rules; direct pushes to main are rejected. Verified
2. Strict Quality Gates Zero-warning policy on linters. Type checking must pass with strict mode enabled. CI blocks PRs on any clippy, ruff, or mypy warning. Verified
3. Hermetic Builds & Zero-:latest All container images are pinned to immutable SHA-256 digests or exact semver tags. Floating tags like :latest are strictly forbidden. KubeLinter and Trivy IaC scans in CI pipelines enforce digest pinning. Verified
4. Human Review on Upstream Sync Upstream releases are evaluated for breaking schema changes or added telemetry before rebasing. Synchronisation PRs require manual human review and green integration tests before merge. Verified
5. Automated CVE Remediation Vulnerabilities tracked across GitHub Project 6 are triaged and assigned fixes autonomously. Hourly cron triggers scanner and remediation workflows across active repositories. Deployed
