Dark Gravity Architecture & Governance

The Dark Gravity Autonomous Software Factory is a Rust-based Continuous Agentic / Continuous Deployment (CA/CD) system designed for zero-trust, security-critical environments. It coordinates specialized multi-agent personas through Spec-Driven Development (SDD), Domain-Driven Design (DDD), and strict cryptographic, kernel, and human-in-the-loop (HITL) boundaries.

Status taxonomy

Every architectural claim, feature, and component across this page carries one of four explicit verification tags:

Verified Confirmed by automated CI suites or published evidence files.
Deployed Running and active in live cluster environments.
Implemented Code written, unit-tested, and tracked in the Rust workspace.
Designed Documented in ADRs, specs, or wiki; full validation pending.

What is the workspace architecture?

Dark Gravity is structured as an Onion Architecture across a 5-crate workspace in Rust Edition 2024 (rust-version = "1.85", verified on 1.97.1). The domain core contains zero external I/O, ensuring that business rules, safety invariants, and cryptographic assertions remain isolated from transport layers.

Crate Name Architectural Layer Role & Responsibilities Status
factory-core Domain Core Pure domain models (Mission, Task), aggregate roots, domain errors, and security traits (SecurityBounds, SecurityValidator) with zero external I/O. Verified
factory-application Application Layer Agent workflows (Rustant, ZeroClaw, DevOpsAgent, DocAgent), Hatchet 6-phase durable DAG definitions, and resilience circuits. Verified
factory-infrastructure Infrastructure Layer External service adapters for Apache Kafka, CloudNativePG (pgvector), HashiCorp Vault, R2R GraphRAG, OpenZiti, S3 storage, and Semantica. Deployed
factory-mcp-server Interface Layer Axum-based Model Context Protocol (MCP) server running on port 8100 that dispatches tool executions and launches gVisor sandbox jobs. Deployed
factory-cli Entry Point Binary entrypoint wiring workspace dependencies, starting the Hatchet worker, running GitPlatformPoller, and hosting the ADR-008 CRD operator controller. Deployed

Enterprise integration interfaces

Dark Gravity integrates into enterprise software factories through three non-invasive, pull-based mechanisms:

  • Outbound Polling (GitPlatformPoller): Periodically polls GitHub/GitLab APIs (every 30–60 seconds) for issues tagged autonomous-mission. It signs mission payloads with an Ed25519 Verifiable Credential and publishes them to Kafka topic mission-input.
  • Interactive PR Directives: Engineers interact with active PRs via comment mentions (such as @darkgravity /status, /interact, /refine, /validate). The poller reacts with eyes (•) and posts structured execution progress.
  • GitOps Delivery: Generated code changes are pushed to isolated remote feature branches, opening formal PRs linked to originating issues (Closes #ID).

How do missions flow through the factory?

Mission execution is coordinated by a crash-resilient Hatchet 6-Phase Durable DAG (cacd-mission-dag) backed by PostgreSQL state checkpoints and MinIO S3 storage. Each step runs with a 30-minute execution timeout to handle long-running compilation and testing tasks safely.

Phase Responsible Agent Execution Details Status
1. Ingestion & Plan RustantAgent (PO) Queries R2R GraphRAG for codebase context, executes Spec-Kit slash commands, and produces atomic, dependency-ordered tasks in tasks.md. Verified
2. Execution ZeroClawAgent (Dev) Consumes tasks via speckit-superpowers-bridge, applying AST-guided code edits inside isolated gVisor micro-sandboxes. Verified
3. Validation ZeroClawAgent (Dev) Executes compile checks, test suites, and linters (cargo test, clippy, pytest) inside the gVisor sandbox. Verified
4. Security Review RustantAgent (Reviewer) Invokes the security_review tool: an LLM-as-a-Judge SAST audit routed via LiteLLM to an independent model family. Enforces score ≥ 8.0/10.0 and records causal lineage in Semantica. Verified
5. Delivery factory-deliver Pushes feature branch, opens a formal PR/MR with linked issues (Closes #ID), and awaits human review. Verified

What is the ADR-008 workspace standard?

Merged in PR #547 and deployed in version v0.2.8, ADR-008 (“CRD & GitOps Workspace Standard” v3.1) transitions the factory from raw pod scheduling to a declarative, Kubernetes-native Custom Resource Definition (AgentWorkspace) managed by an active controller in factory-cli.

Declarative CRD Lifecycle

The AgentWorkspace CRD (agentworkspaces.darkgravity.io/v1alpha1) declares the mission contract, repository target, branch, and resource boundaries. The controller reconciles workspaces through state phases: Pending → Cloned → Active → Completed / Failed.

Strict Admission Bounds

ValidatingAdmissionPolicies (dg-sandbox-bounds-jobs and dg-sandbox-bounds-pods) enforce hard limits in sandbox namespaces: memory ≤ 30 MiB, CPU ≤ 250m, and forbid ephemeral containers and privilege escalation.

ADR-008 Status: Merged & Deployed (v0.2.8)

The CRD definitions, admission policies, and controller runtime are merged in PR #547 and verified through integration test suites. Sandbox job templates declare explicit requests (16Mi / 50m) alongside limits to satisfy cluster admission constraints.

What are the security boundaries?

Dark Gravity enforces layered defense-in-depth across the network, process memory, container kernel, and human authority levels:

Cryptographic Non-Human Identity (NHI)

Agents sign all mission state transitions and artifacts using Ed25519 keypairs wrapped in W3C Verifiable Credentials (Ed25519Signature2020).

Verified

Forensic Memory Zeroization

Sensitive credential buffers implement Zeroize and ZeroizeOnDrop, wiping memory immediately on drop. Benchmarked via Criterion at 54.2 ns.

Verified

Predictive FinOps Guard

LiteLLM routes inject Virtual Tags (x-vtags-*). FinOpsAgent samples spend every 60s, detecting velocity anomalies (>+$1.00/min) and triggering HardStops at 90% budget ($45 of $50).

Verified

Strict Human-in-the-Loop Policy

Autonomous agents can open PRs, push branches, and resolve CI failures, but merging to default branches (main) is strictly a manual human action. Direct automated merges are forbidden.

Verified
