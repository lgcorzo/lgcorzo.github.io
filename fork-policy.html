Fork policy: why the lab forks open-source projects

Out of 64 public repositories across the lab, 42 are maintained as independent open-source forks. Here is why I fork them, the five rules that govern them, and the complete catalog grouped by purpose.

In one minute

  • Forks protect autonomous agent workflows from unexpected upstream API breaks and schema changes.
  • Security updates are triaged and patched autonomously through GitHub Project 6 and Jules.
  • Every fork enforces five quality gates: branch protection, zero-warning linters, SHA-256 digest pinning, human review on upstream rebases, and CVE scanning.
  • 17 of the 42 forks are low-level Go libraries (SIMD acceleration, hashing) needed by the sovereign S3 storage tier.

Why fork instead of using upstream packages directly?

An autonomous system running continuous coding tasks cannot afford unexpected upstream churn. Forking critical dependencies provides four concrete engineering advantages:

1. Deterministic SDD contracts

Autonomous agents need deterministic CLI arguments, flags, and JSON schemas. In forks like spec-kit and speckit-superpowers-bridge, command interfaces and output schemas are locked so that agent runs do not break when upstream repositories change behaviour.

Status: Verified

2. Immediate security patching

When Dependabot or CodeQL identifies a CVE in a dependency, the lab does not wait weeks for an upstream maintainer to merge a fix. The hourly scanner in GitHub Project 6 and Jules opens and tests patches immediately.

Status: Deployed

3. Uniform quality gates

Every maintained fork is brought under the same automated linting and security rules: strict clippy or ruff settings, automated vulnerability audits, and pinned dependency versions.

Status: Verified

4. Build hermeticity

Containers and binaries build cleanly from pinned tags and publish to ghcr.io/lgcorzo/*, decoupling internal builds from external registry downtime or license changes.

Status: Deployed

What five rules govern every fork?

Each of the 42 forks must satisfy five strict engineering standards. No fork is exempt.

Rule Standard Enforcement mechanism Status
1. Remote and branch hygiene Upstream clean tags are tracked on dedicated tracking branches. Custom modifications live on isolated branches. Branch protection rules reject direct pushes to main. Verified
2. Strict quality gates Zero-warning policy across linters and strict type-checking mode. CI blocks merges on any clippy, ruff, or mypy warning. Verified
3. Hermetic builds & zero :latest All images pinned to immutable SHA-256 digests or semver releases. Floating tags are rejected. KubeLinter and Trivy scans in CI enforce digest pinning. Verified
4. Human review on upstream rebases Upstream sync PRs require automated test passes and manual sign-off before merge. Strict Human-in-the-Loop policy. No agent merges to default branches. Verified
5. Automated CVE triage Vulnerabilities tracked in GitHub Project 6 are reviewed hourly. Hourly cron triggers scanner and Jules remediation workflows. Deployed

How is dependency security verified?

Forked code is not trusted blindly. Dependencies undergo continuous automated verification:

Automated threat triage

Project 6 tracks vulnerabilities across all 64 public repositories. Dependabot alerts, CodeQL queries, and pip-audit / cargo-audit runs feed into a centralized triage queue.

Evidence: threat-model.md

Process micro-isolation

When an agent executes code or tests from a dependency, it runs inside a restricted gVisor sandbox with CAP_DROP_ALL, read-only root filesystems, and strict CPU/memory limits.

Evidence: security-tests.md
