Lifecycle: how one mission goes from issue to pull request

This page tells the story of a single mission. For the parts and where they run, see Architecture.

In one minute

  • A person writes an issue and adds a label. Agents plan, code, test and review.
  • The result is a pull request, never a merge.
  • Four human decision points are defined. Only the last one is visible in code today.
  • Failures are caught by retries, a repeated-diff check and a spend limit.

What happens, step by step?

  1. A person opens an issueThe issue carries a label such as autonomous-mission and says what is wanted and what limits apply.
  2. The poller picks it upIt asks the Git host for new labelled issues, signs the request with an Ed25519 key, and publishes it to the Kafka topic mission-input.
  3. PlanThe step rustant-plan reads context from R2R and writes a spec, a plan and a task list.
  4. ExecuteThe step zeroclaw-execute starts a sandbox job under gVisor and applies each task.
  5. ValidateThe step zeroclaw-validate runs the tests and linters in that sandbox.
  6. ReviewThe step rustant-review asks an AI judge to score the diff for security. A score under 8.0 out of 10 rejects it.
  7. DeliverThe step factory-deliver pushes a branch, opens a pull or merge request that links the issue, and comments that it is ready for a human reviewer.

Status: Deployed Source: autonomous_mission.rs and poller_service.rs.

Where do people decide?

The wiki defines four human decision points, called vertices. Automation handles the work between them.

VertexWho and whenStatus
1. Strategic injectionThe product owner decides what mission to start.Designed
2. Sprint mobilizationThe tech lead releases work for execution.Designed
3. Exception overrideThe architect steps in when a safety limit stops a mission.Designed
4. Categorical scrutinyA senior reviewer reads and merges the pull request.Implemented

Vertex 4 is implemented in the sense that the pipeline stops at an open pull request. Source: hitl_governance.md.

Reviewers can also comment on a pull request with directives such as /status, /refine and /validate. The poller reads them in comment_control.rs. Implemented

What happens when something fails?

A worker dies mid-step

Hatchet notices the lost worker and runs the step again on another one. Saved state avoids repeating finished work.

Verified reliability-tests.md. One killed pod in a sandbox environment.

The agent loops on the same fix

A circuit breaker hashes each diff and stops when it sees the same change again.

Implemented circuit_breaker.rs

Spend runs away

The budget guard halts missions at 90% of the daily limit. The default limit is $50.

Implemented finops.rs

A step is rejected by the sandbox rules

If a job asks for more than 30Mi or 250m, or leaves out requests, the cluster refuses it at creation.

Deployed Lab note on ADR-008

Can it fix a broken pipeline?

There is a second entry point. When a CI pipeline fails, a classifier labels the error and the factory can publish a repair mission to the same mission-input topic. The same five steps then run.

Implemented Source: pipeline_remediation.rs and spec 005-pipeline-error-remediation. A jules-remediator deployment runs in the cluster, but this page does not claim it executes that workflow.

What is not proven yet?

  • Vertices 1 to 3 are defined in the wiki and are not enforced by code that was checked.
  • No test shows a mission surviving many hours or many nodes failing.
  • The review score comes from a language model. It is a filter, not a proof of security.
  • The completed run on v0.2.8 is not saved as an evidence file.
