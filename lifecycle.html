The 4 Human-in-the-Loop (HITL) Checkpoints

Branch protection and review gates are designed to prevent agents from merging code on their own. The human steers intent and keeps the veto.

HITL Vertex 1

Strategic Injection

Human Product Owner: Authors high-level business Epics or issues in Jira, GitHub, or GitLab, tagged with autonomous-mission. The human defines why and what value is required.

HITL Vertex 2

Sprint Mobilization

Human Tech Lead: Reviews the generated Spec-Kit artifacts (spec.md, plan.md, tasks.md) and approves the sprint. Prevents runaway token and compute spending.

HITL Vertex 3

Exception Override

Human System Architect: Ideally no intervention during active loops. Alerts fire only if Aethelgard hits the 3-retry limit or a spend velocity trip trips to Agent-Stuck. The architect untangles the edge case.

HITL Vertex 4

Categorical Scrutiny

Human Senior Reviewer: Conducts final code review on remote Pull/Merge Requests. Agents are physically forbidden from auto-merging. Human validates architecture and business logic before manual merge.

Deep Architectural Breakdown

The Six Specialized Stages of Dark Gravity

Each phase implements hardened security primitives, bounded contexts, and deterministic contracts. Explore the technical mechanics behind each operational stage.

Phase 1: Ingestion & Cryptographic Identity

Air-Gapped Outbound Polling & W3C Non-Human Identity (NHI) Signing

To achieve a zero-trust, air-gapped perimeter, Dark Gravity firmly rejects all open inbound webhooks. Inbound HTTP ports create external attack surfaces and dependency on external proxy tunnels (such as ngrok or Cloudflare Tunnels). Instead, the native Rust GitPlatformPoller daemon (factory-cli poller) queries Jira, GitHub, and GitLab APIs via outbound HTTPS requests every 30 to 60 seconds.

Cryptographic Ingestion Workflow

  • Target Discovery: Scans for issues carrying the mandatory autonomous-mission or dark-gravity label.
  • Resource Constraint Extraction: Parses hardware directives like [RESOURCE_LIMIT: RAM <= 30Mi, CPU <= 250m] directly from issue descriptions.
  • Ed25519 W3C VC Generation: Signs mission provenance with an Ed25519 keypair from HashiCorp Vault representing Non-Human Identity (did:factory:dark-gravity-euskadi).
  • Kafka Event Bus: Serializes payload to MissionInput and publishes to the mission-input topic in Confluent Kafka.

Phase 2: Spec-Driven Development

The 7-Step Spec-Kit Slash-Command Pipeline & Causal Governance

Dark Gravity completely replaces free-form LLM code generation with Spec-Driven Development (SDD). Before a single byte of code is written in a sandbox, the Product Owner Agent (Rustant) queries R2R GraphRAG for architectural context and runs a deterministic Spec-Kit pipeline through the spec_kit_tool MCP endpoint.

1. /speckit-constitution

Enforces sovereign principles: Zero Trust, mTLS 1.3, gVisor resource caps, and anti-loop safeguards.

2. /speckit-specify

Combines R2R context with issue intent to create spec.md: defining what and why without stack pollution.

3. /speckit-clarify

Runs up to 5 automated Q&A cycles against edge cases before architecture begins, eliminating requirements ambiguity.

4. /speckit-plan

Outputs technical blueprints (plan.md, research.md, contracts/), pinning crates and interfaces.

5. /speckit-tasks

Decomposes plan into atomic, dependency-ordered tasks (tasks.md) with [P] parallel flags.

6. /speckit-taskstoissues

Converts tasks into tracked backlog sub-issues with injected hardware clamping markers.

7. Semantica-AGI Conflict Check

Validates generated plan against organizational ontology to catch architectural contradictions before sandbox ignition.

Phase 3: Durable Orchestration

Superspec Bridging, Hatchet Long-Term DAG & Crash Checkpoints

The speckit-superpowers-bridge (Superspec) parses Spec-Kit tasks.md into structured domain entities and maps them into Hatchet's durable develop-task sub-workflows. Hatchet provides at-least-once, durable execution semantics; how well this holds up in the lab is one of the things being tested.

S3 Checkpoint State Recovery

As the Developer Agent completes each atomic task (e.g. T001, T002), execution snapshots (BridgeState) are flushed to MinIO S3 in the dg-factory-checkpoints bucket and CloudNativePG PostgreSQL. If a worker pod crashes or is terminated due to memory bounds, Hatchet restarts execution exactly at the first pending task without repeating completed AST code surgery or wasting LLM tokens.

Phase 4: Sandboxing & Validation

gVisor Micro-Sandboxing, AST Surgery & Aethelgard Circuit Breaker

Execution occurs exclusively in ephemeral gVisor (runsc) user-space sandboxes configured with target limits of RAM ≤ 30 MiB and CPU ≤ 250m. AST code mutations are executed via native ADK-Rust, followed by test and security gates.

1. ADK-Rust AST Surgery

Tree-sitter AST search-and-replace algorithm applies localized mutations directly to Rust files without external subprocess overhead or regex hallucinations.

2. In-Memory Secret Zeroization

All JIT tokens and credentials derive #[derive(Zeroize, ZeroizeOnDrop)], so they are overwritten in memory when dropped. Timing figures from micro-benchmarks are not treated as production guarantees.

3. SAST LLM-as-a-Judge

Heterogeneous frontier models score patches. Scores < 8.0/10 or detected vulnerabilities trigger the Aethelgard loop (max 3 retries) or freeze to Agent-Stuck.

Phase 5: Delivery & Directives

GitOps Atomic Delivery & Interactive Pull Request Steering

Approved patches are committed atomically via REST APIs directly to feature branches (specs/NNN-<feature>) and open Pull/Merge Requests targeting main. Human developers interactively steer the bot on PR threads via command directives.

Interactive Directives (@darkgravity)

  • @darkgravity /status — Queries factory health, DAG step, and token spend.
  • @darkgravity /refine <prompt> — Triggers ZeroClaw to apply localized AST edits.
  • @darkgravity /spec <prompt> — Instructs Rustant to re-evaluate Spec-Kit spec.md.
  • @darkgravity /validate — Reruns cargo test suite and SAST security check.
  • @darkgravity /retry — Restarts the Aethelgard remediation loop.

Low-Noise PR Protocol

The poller places an immediate "eyes" (👀) reaction upon comment detection to acknowledge receipt without posting spam comments. It strictly ignores self-authored bot accounts to prevent infinite loops, and posts a single comprehensive summary when the directive finishes.

Strict Manual Merge Policy: Agents are physically forbidden from merging to main. Merge authority rests solely with the human Senior Reviewer (HITL Vertex 4).
Phase 6: Living Knowledge & C4

Tree-sitter AST GraphRAG, Living C4 Models & Open Knowledge Format (OKF)

When a PR is merged into main, the autonomous lifecycle doesn't end: it automatically updates living corporate memory. The deepwiki-rs daemon parses AST diffs, updates R2R GraphRAG in pgvector, and dispatches the Documentation Agent (DocAgent) using the Superpowers framework to regenerate C4 architecture diagrams and OpenWiki documentation.

DocAgent Superpowers Pipeline

  1. writing-plans: Decomposes wiki updates into 2–5 min atomic tasks.
  2. dispatching-parallel-agents: Spawns isolated subagents per wiki page.
  3. subagent-driven-development: Loads only targeted R2R sub-graphs.
  4. verification-before-completion: Enforces OSR < 5% gate.
  5. requesting-code-review: Validates C4 Mermaid syntax and Markdown.
  6. finishing-a-development-branch: Commits pages and packages EU R&D grants.
